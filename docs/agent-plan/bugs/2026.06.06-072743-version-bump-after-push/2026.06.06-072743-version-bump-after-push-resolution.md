# Resolution: version-bump-after-push

## Fix applied

Reworked the versioning model to **bump-at-release on main**, instead of
bumping per push.

The pre-push hook (`.githooks/pre-push`) previously **blocked any push that
touched releasable files (`skills/`, `scripts/`, …) without also changing a
version file**, forcing a manual bump on every feature-branch push. That is
unworkable with concurrent development: a single linear release counter cannot
be assigned per parallel branch — two open branches both pick the same next
number and then conflict on the version files (`package.json`, the lockfile,
`.claude-plugin/plugin.json`, etc.). It also conflated "a feature was pushed"
with "a release happened," inflating the version (5.1.3 → 5.1.4 → 5.1.5)
without corresponding releases.

The hook now enforces **only version-file drift** — that the six declared files
in `.version-bump.json` agree — and no longer requires a bump just because
releasable files changed. Version bumps happen **once per release on `main`**:
`scripts/bump-version.sh <next>`, then tag and publish. Feature branches never
touch the version.

`test/version-hooks/run-test.sh` was updated to assert the new behavior: a
releasable change without a bump is allowed (on both main and a new branch),
while a half-edited version state (drift) still blocks the push.
